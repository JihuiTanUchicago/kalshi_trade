# Native Bitcoin perps live execution contract

2026-10-23 / official-documentation review and isolated client implementation / integration handoff. Owned artifacts are this document, new `app/adapters/kalshi_perps/kalshi_perps_trading_client.py`, and its new synthetic tests. No private account, provider API, order, schema, service, deployment, or production operation was performed. The client is offline verified; this is not live acceptance.

**User decision:** a person confirms every order. Kalshi controls permitted leverage, margin and exposure; add no Tau dollar, exposure, or leverage caps. The earlier proposed 1×/$100/$250 defaults are superseded. Technical guards, immutable confirmation, account ownership, exact units, freshness, reconciliation and fail-closed handling remain. Build a dedicated perps path; retain the binary engine and its execution controls unchanged.

## Environment, credentials, authentication and approval

Use only these fixed REST origins, followed by `/trade-api/v2`: production `https://external-api.kalshi.com`; demo `https://external-api.demo.kalshi.co`. Public-data success and demo success do not prove the production user's trading approval. Production access is rolling out per member. Margin cash is separate from predictions cash. [Perps API overview](https://docs.kalshi.com/margin), [Margin account](https://help.kalshi.com/en/articles/15357608-your-perpetuals-margin-account).

Every private request carries `KALSHI-ACCESS-KEY`, `KALSHI-ACCESS-TIMESTAMP` (Unix milliseconds string), and `KALSHI-ACCESS-SIGNATURE` (base64). Sign UTF-8 `timestamp + UPPERCASE_HTTP_METHOD + full_path_without_query`, e.g. the path `/trade-api/v2/margin/orders`, using RSA-PSS/SHA-256, MGF1/SHA-256 and a digest-length salt. Do not sign the origin, query string or JSON body. Rebuild timestamp/signature for each request. REST also supports Ed25519, but the existing RSA-only key store is a valid initial subset. [Authenticated requests](https://docs.kalshi.com/getting_started/quick_start_authenticated_requests).

Reuse `repository.get_kalshi_key(cur, uid)` for production and `get_kalshi_dev_key(cur, uid)` for demo, then `kalshi_account.credentials_from_row(uid,row)`. These store AES-256-GCM ciphertext bound to the user ID in separate tables. Existing ciphertext is not cryptographically environment-bound; the service must select the correct table and retain explicit environment context. Never fall back to global `PROD_*` credentials, the binary cash helper, `order_submitter`, or a different user's key. Decrypt only in memory, never send keys to the frontend/models or persist/log headers, signatures, PEM, exception bodies or raw account responses. The transport must not inherit `.netrc`, cookies, session auth, ambient headers or arbitrary URLs; allow an explicit credential-free proxy only if required by the deployment.

Kalshi requires eligible users to complete KYC, apply for margin access, obtain approval, and complete its educational tutorial. The app must not automate or bypass those steps. Require authenticated `GET /margin/enabled` to return `enabled is True`; false, missing or malformed means unavailable. A working predictions key proves neither this approval nor margin funds or write permission. [Applying for access](https://help.kalshi.com/en/articles/15357656-applying-for-perpetuals-access), [Enabled status](https://docs.kalshi.com/margin-rest/exchange/get-enabled-status).

## Exact native surface

All paths below are relative to `/trade-api/v2`. Financial fields stay finite decimal strings/`Decimal`; never cents or binary YES/NO complements. Response descriptions are the documented native shape, with optional fields validated when present.

| Purpose | Method and path | Native contract and source |
| --- | --- | --- |
| Entitlement | `GET /margin/enabled` | `{enabled: boolean}`; signed. [Reference](https://docs.kalshi.com/margin-rest/exchange/get-enabled-status) |
| Exchange state | `GET /margin/exchange/status` | `exchange_active`, `trading_active`; optional estimated resume time is not guaranteed. Perps does not supply the predictions-only transfer/index-status fields shown in generated examples. [Reference](https://docs.kalshi.com/margin-rest/exchange/get-exchange-status) |
| Instrument | `GET /margin/markets/{ticker}` | Native `market` object: ticker/title/market_id/market_version/exchange_index, contract_size/underlying_multiplier/tick_size, status/fractional_trading_enabled/schedule and optional mark/reference/leverage metadata. [Reference](https://docs.kalshi.com/margin-rest/market/get-market) |
| Depth | `GET /margin/markets/{ticker}/orderbook` | `{orderbook:{bids:[[price,count],…],asks:[[price,count],…]}}`; no binary complement. Optional `depth` is documented; do not invent a server quote timestamp absent from the body. [Reference](https://docs.kalshi.com/margin-rest/market/get-market-orderbook) |
| Submit | `POST /margin/orders` | Required fields listed below; 201 returns a flat acknowledgement. [Reference](https://docs.kalshi.com/margin-rest/orders/create-order) |
| Retrieve | `GET /margin/orders/{order_id}` | `{order:{order_id,client_order_id,ticker,side,price,fill_count,remaining_count,last_update_reason,created_time,last_update_time,…}}`; optional subaccount query. [Reference](https://docs.kalshi.com/margin-rest/orders/get-order) |
| List orders | `GET /margin/orders` | `{orders:[],cursor}`; ticker/min_ts/max_ts/status/limit/cursor/subaccount filters. Limit 1–10000. Status is free string with no native enum in the rendered reference: omit an unverified value. [Reference](https://docs.kalshi.com/margin-rest/orders/get-orders) |
| Cancel remainder | `DELETE /margin/orders/{order_id}` | `{order_id,reduced_by,client_order_id?}`; optional subaccount query. `reduced_by` is canceled contracts, not filled contracts. [Reference](https://docs.kalshi.com/margin-rest/orders/cancel-order) |
| Amend | `POST /margin/orders/{order_id}/amend` | Required side/price/count; ticker or market_id, original/updated client_order_id and expiration_time are optional; subaccount is a query parameter. Documented for future GTC support; exclude from the first IOC service. [Reference](https://docs.kalshi.com/margin-rest/orders/amend-order) |
| Positions | `GET /margin/positions` | `{positions:[{subaccount,market_ticker,position,entry_price,unrealized_pnl,fees,is_portfolio,margin_used,roe,…}]}`. Query subaccount/ticker; no pagination documented. [Reference](https://docs.kalshi.com/margin-rest/portfolio/get-positions) |
| Fill ledger | `GET /margin/fills` | `{fills:[{fill_id,order_id,is_taker,side,count,created_time,ticker,price,entry_price,fees,realized_pnl,…}],cursor}`. Query subaccount/limit/cursor/min_ts/max_ts; limit 1–1000. No ticker/order_id filter is documented; filter locally after complete bounded pagination. [Reference](https://docs.kalshi.com/margin-rest/portfolio/get-fills) |
| Margin balance | `GET /margin/balance?compute_available_balance=true` | `{subaccount_balances:[{subaccount,position_value,account_equity,maintenance_margin,initial_margin,resting_orders_margin,available_balance}],settled_funds}`. The flag is essential: omitted/false reports available_balance=0 without computing it. It raises the documented request cost from 5 to 50 tokens. [Reference](https://docs.kalshi.com/margin-rest/portfolio/get-balance) |
| Actual leverage/risk | `GET /margin/risk` | `account_leverage`, `total_position_notional`, `total_maintenance_margin`, and per-position `position_notional`, `maintenance_margin_required`, `position_leverage`, `estimated_liquidation_price`, mark and account identity. [Reference](https://docs.kalshi.com/margin-rest/risk/get-risk) |
| Broker limits | `GET /margin/notional_risk_limit` | `default_notional_value_risk_limit`, `notional_value_risk_limits_by_market_ticker`, `current_usage_by_market_ticker`, `member_notional_value_risk_limit`, `effective_account_notional_value_risk_limit`. Do not confuse an FCM's omnibus limit with one customer's spending authority. [Reference](https://docs.kalshi.com/margin-rest/risk/get-notional-risk-limit) |
| Risk parameters | `GET /margin/risk_parameters` | `liquidation_margin_ratio_threshold`, `queue_entry_margin_ratio_threshold`, `initial_margin_multiplier` map. These are system parameters, not a complete per-order initial-margin quote. [Reference](https://docs.kalshi.com/margin-rest/risk/get-risk-parameters) |
| Effective fees | `GET /margin/fee_tiers` | Per-market `maker_fee_rates`, `taker_fee_rates`, decimal fractions; no tier number. `/margin/fee_tier_rates` is the fee schedule, not the user's effective rate. [Effective rates](https://docs.kalshi.com/margin-rest/fees/get-fee-tiers), [Schedule](https://docs.kalshi.com/margin-rest/fees/get-fee-tier-rates) |
| API budgets | `GET /account/limits/perps` | Deliberate path exception outside `/margin`: `usage_tier`, `read`/`write` with `refill_rate`/`bucket_capacity`. [Reference](https://docs.kalshi.com/margin-rest/account/get-perps-account-api-limits) |

Do not expose account-wide cancel-all, transfers, key creation, account creation, risk-limit mutation, or binary order endpoints through this client. In particular, cancel-all can affect new orders for a minute and orders outside the app's ownership. Cancel only tracked perps order IDs belonging to the authenticated user and environment.

## Smallest first order

Freeze one immutable body before confirmation. Proposed canonical shape:

```json
{
  "client_order_id": "<server-generated UUID>",
  "ticker": "<verified native BTC ticker>",
  "side": "bid",
  "count": "1.00",
  "price": "<positive tick-valid USD per-contract limit>",
  "time_in_force": "immediate_or_cancel",
  "self_trade_prevention_type": "taker_at_cross",
  "post_only": false,
  "cancel_order_on_pause": true,
  "reduce_only": false,
  "subaccount": 0,
  "market_version": 1
}
```

Placeholders and version 1 are illustrative; fetch the actual ticker/version. Native required fields include side/TIF/STP even though generated examples omit them. There is no `type`, binary `action`, `yes_price`, or leverage field. Bid buys/increases long or reduces short; ask sells/increases short or reduces long. Native TIF values are IOC, FOK, GTC strings above; DAY is not an enum. `reduce_only=true` is accepted only with IOC/FOK. Use IOC for entry and explicitly confirmed reduce-only exits; no resting orders, synthetic market orders, amendments or automatic retries initially. Positive `market_version` provides a 409 mismatch check; 0 disables it. [Create-order field table](https://docs.kalshi.com/margin-rest/orders/create-order), [Order directions and types](https://help.kalshi.com/en/articles/15357617-order-types).

The existing verified normalization defines native prices as USD per contract and BTC units as `count × contract_size × underlying_multiplier`; do not multiply the USD price by the multiplier twice. Retain and validate native contract metadata and tick alignment with exact decimals. BTC help specifies a minimum of one contract; whole positive contracts are the initial valid subset even if fractional trading is enabled. Do not round a user's quantity upward. No universal maximum native order size is documented in the reviewed create schema; do not invent one. Broker product/account limits remain authoritative. [BTC specifications](https://help.kalshi.com/en/articles/15357587-btc-perpetual-futures-contract-specifications), [Native metadata](https://docs.kalshi.com/margin-rest/market/get-market).

**Leverage:** user-selected quantity determines notional and resulting leverage through Kalshi's margin system. Submit no invented `leverage`, isolated/cross switch or locally inferred margin amount. Do not cap quantity at `account_equity / price`, assume 1×, promise “maximum leverage,” or invert one multiplier into guaranteed buying power. Show confirmed limit notional, an explicitly estimated fee from the user's effective rate, fresh available margin and current broker leverage; Kalshi evaluates the order against its current tiered requirements. A broker rejection is a real rejection, not permission to resize/resubmit automatically.

## Confirmation, submission and normalized results

The business service owns database state and per-user serialization; the transport owns only fixed-host HTTP/signing and schema validation. Implemented interface: `Client(credentials_tuple, environment='production', proxy_url=None)` context manager; `enabled_status()`, `exchange_status()`, `market(ticker=None)` / `instrument()`, `orderbook(ticker)`, `balance()`, `positions(ticker=None)`, `risk()`, `notional_risk_limit()`, `fee_tiers()`, `api_limits()`, `orders(ticker=None,min_ts=None)`, `fills(min_ts)`, `order(order_id)`, `submit_order(body)`, `cancel_order(order_id)`. Each result includes environment and local retrieval time; market returns the existing verified normalized instrument, other readers keep validated native wrappers, orders/fills exhaust bounded pagination and add `complete=True` only after its final page. The service adds local user/intent ownership. Monetary values remain decimal strings.

1. Preview using the session user's correct encrypted key and fresh entitlement/exchange/market/depth/balance/position/fee reads. Verified BTC must be active, the exchange must permit trading, and any explicit native closed schedule blocks submission. Do not treat a null schedule as affirmative permission. BTC's documented 24/7-except-maintenance rule plus fresh exchange state is distinct evidence. Reject crossed/empty required depth, stale/failed reads, unknown units/version, or an unreconciled prior intent. REST orderbook freshness measures a newly retrieved response; it is not proof of the last underlying quote update. Use a short explicit preview TTL and revalidate immediately before submit.
2. Persist the exact body, user/environment/subaccount, one-use confirmation token, canonical digest and expiry. Display side, whole-contract quantity, BTC quantity, limit price, worst limit notional, estimated exchange fees, and reduce-only purpose. The user confirms that exact proposal; no post-confirmation change in limit, size, direction or account. Requotes require another confirmation. Primary subaccount 0 is the initial subset; restricted keys for another account fail clearly rather than silently switching.
3. Claim the intent durably before the one HTTP POST. A duplicate UI confirmation returns existing state. Scope the serialization to user/environment/subaccount, including previous unknown submissions. Do not hold a database transaction open across network I/O. Re-read key identity and feature state before signing; a deleted/replaced key invalidates the preview.
4. Parse 201 as flat `order_id`, `fill_count`, `remaining_count`, optional echoed `client_order_id`, `average_fill_price`, `average_fee_paid`. The provider order ID is documented only as a string, not guaranteed UUID. For IOC, remainder is final after cancellation; nonzero/malformed remainder, contradictory IDs/counts, or missing positive-fill economics require reconciliation. `average_fee_paid` is per contract, so acknowledged total fee is `fill_count × average_fee_paid`, not that field alone. REST fills establish actual accounting. [Acknowledgement semantics](https://docs.kalshi.com/margin-rest/orders/create-order).
5. Client-order IDs are required but the reviewed docs give no hard deduplication window or exactly-once guarantee. Never retry an ambiguous mutation automatically. Timeout, disconnect, invalid success body or 5xx after POST becomes `unknown`, keeping the intent locked. Recover through bounded complete order/fill scans matched to persisted client/order IDs, then fresh positions/balance; incomplete pagination is unknown, not no order. Don't mint a new client ID and repeat. Native rendered order records expose no documented status enum; use local `submitting`, `unknown`, `reconciling`, `terminal_filled`, `terminal_partial`, `terminal_unfilled` states backed by acknowledgement/ledger facts.
6. A cancel acknowledgement only cancels the resting remainder; fills may race it. Reconcile order, deduplicated fills and position before final accounting. A cancel 404 is not proof that no fill occurred. A reduce-only exit uses the latest signed position and opposite side; it never intentionally flips a position. Every additional order, including another attempt after a confirmed no-fill or a partial close, requires another human confirmation. External resting orders/positions remain visible broker state; do not cancel or adopt them silently.

Normalize REST fill IDs separately from WebSocket trade IDs until a documented or tested mapping exists. Persist only the needed decimal quantities, timestamps, IDs and states; audit amounts and ownership without raw account bodies. Broker errors should map to bounded sanitized codes. Transport/schema failure must not become zero margin, zero fills, or a success state.

## Throttling and WebSocket reconciliation

Perps has separate read/write token buckets from predictions; REST/FIX share budgets, and perps order writes can be shard-scoped. Query the user's actual perps limits. Current docs say 429 lacks Retry-After/rate-limit headers; use bounded exponential backoff for safe reads. Reserve cancellation/reconciliation capacity and use hard response, pagination, cursor, runtime and retry bounds. Exhausting a bound is incomplete state. Mutation retries require explicit reconciliation and business-service control, never a generic HTTP retry adapter. [Rate limits](https://docs.kalshi.com/getting_started/rate_limits).

Native WebSocket hosts are production `wss://external-api-margin-ws.kalshi.com/trade-api/ws/v2/margin` and demo `wss://external-api-margin-ws.demo.kalshi.co/trade-api/ws/v2/margin`, authenticated during handshake with the same method/path signing convention. Use `orderbook_delta`, `ticker`, `fill`, `user_orders`; timestamps use milliseconds (`*_ms`). The book channel starts with a snapshot and then deltas, and supports requesting a fresh snapshot. Sequence/sid gaps, reconnects or stale snapshots invalidate the local book until rebuilt. Private fill notifications use `trade_id`, `fee_cost`, `post_position`; REST fills use `fill_id` and `fees`. Do not assume private notifications supply durable replay, sequence completeness, or one-to-one REST IDs. On reconnect reconcile REST orders/fills/positions/balance before allowing further orders. Ping is every 10 seconds and requires Pong. [Connection](https://docs.kalshi.com/margin-ws/websockets/websocket-connection), [Book](https://docs.kalshi.com/margin-ws/websockets/orderbook-updates), [User fills](https://docs.kalshi.com/margin-ws/websockets/user-fills), [User orders](https://docs.kalshi.com/margin-ws/websockets/user-orders), [Keep-alive](https://docs.kalshi.com/margin-ws/websockets/connection-keep-alive), [Hosts/conventions](https://docs.kalshi.com/margin).

The smallest manual IOC release can reconcile through REST without claiming a WebSocket implementation; streaming integration is a separate acceptance item. Required offline evidence includes exact signing/body tests, environment/user isolation, decimals/ticks, unknown POST outcomes, duplicate confirmations, partial fills, cancel races, wrong-account records, stale/closed state and pagination failure. Demo validates protocol and reconciliation only; production eligibility, real margin, fees and one explicitly confirmed production order remain separate acceptance facts. Nothing in this document changes the prior incomplete historical replay coverage result.

## Implemented client evidence and boundary

The isolated client follows the names above, preserves the approved count/price strings without rewriting the immutable body, and snapshots the body before metadata I/O. Native unit multiplication occurs only when the service calculates BTC quantity; the client returns native USD-per-contract fill prices. It applies no Tau leverage/exposure/notional caps. Its private responses are transient return values; the client emits no logs and persists nothing.

`Error(code,message,status,rejected=False,uncertain=False)` exposes sanitized classifications only. Writes use one attempt and adapters with zero retries. Network/timeouts, malformed success, redirects, 429, 5xx and ambiguous 409s remain uncertain; a cancel 404 is also uncertain. Positive-fill acknowledgements require known price and per-contract fees, counts within the order/native step, no remaining IOC quantity and no fill beyond the confirmed limit. Unknown acknowledgements remain reserved for service reconciliation. No-fill acknowledgements retain absent economics rather than fabricating zero prices. GETs also use one attempt. Fixed size/time/page/row limits reject incomplete state, not silently truncate it.
